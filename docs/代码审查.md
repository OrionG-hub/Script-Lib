### 优先优化

#### 1. TeleBox Docker：依赖安装位于每次启动路径

- 位置：`Telebox/telebox-docker.sh:248`、`Telebox/telebox-docker.sh:288`、`Telebox/telebox-docker.sh:318`。
- 证据：交互式 `run --rm` 与后台服务命令均包含 apt 更新、NodeSource 配置、Node.js 和全局 PM2 安装。后台命令仅对 TeleBox 安装脚本做文件存在判断，没有跳过前面的环境安装步骤。
- 影响：交互配置与正式服务启动重复做环境准备；后续容器启动仍需执行这些联网命令，延长启动并增加网络故障影响。
- 建议：将系统依赖、Node.js 和 PM2 固化到同一构建镜像，交互配置和后台服务复用；启动命令只运行服务，升级放到显式构建/更新流程。
- 需确认：是否接受增加 Dockerfile，以及镜像构建/更新方式。本次不擅自改变部署架构。

#### 2. TeleBox PM2：切换账号和普通更新无条件安装依赖

- 位置：`Telebox/installTeleBox.sh:304`、`Telebox/installTeleBox.sh:498`、`Telebox/installTeleBox.sh:517`。
- 证据：`switch_login` 在停止实例和清理登录配置之前，调用系统依赖检查、仓库更新和项目依赖安装。安装/更新也无条件调用 `install_node_deps`。存在锁文件时执行 `npm ci`。
- 验证：替身流程测试确认调用顺序为系统依赖 → 更新仓库 → 安装项目依赖 → 停止实例 → 清理登录信息 → 登录 → 启动。已核对本机 npm 官方文档：`npm ci` 会先删除已有 `node_modules`。
- 建议：将切换账号与代码升级解耦；普通更新根据 package.json、锁文件、Node/npm 版本及平台指纹判断是否需要重装，保留 `deps` 的强制重装语义。避免仅判断目录存在就跳过修复。
- 需确认：切换账号是否必须同时更新代码；新跳过策略是否接受保留显式强制重装入口。

#### 3. Docker / PM2：列表查询逐个启动命令

- 位置：`Telebox/telebox-docker.sh:49`、`Telebox/installTeleBox.sh:172`。
- 证据：Docker 先列出名称，再对每个容器调用 inspect；PM2 每个实例分别执行 describe 和 pid。交互菜单会重复走列表路径。
- 验证：隔离替身测试中，20 个容器触发 21 次 Docker 调用，20 个已注册实例触发 40 次 PM2 调用；这是调用次数，不是实测服务耗时。
- 建议：Docker 一次返回名称与状态，PM2 一次获取进程快照并在本地建立索引。快照只在同一轮列表中复用，操作进程后刷新，避免长期缓存导致状态过期。
- 优先级：中；多实例时收益更明显，单实例收益有限。

#### 4. Sub-Store：每个名称遍历全部地区别名

- 位置：`substore/rename.js:112`、`substore/rename.js:177`、`substore/rename.js:235`。
- 证据：每次 operator 调用重新构造地区识别器；每个名称都执行全部 compiledAliases 的正则，即使已经匹配到前部的常用地区名称也继续遍历。
- 验证：本机 Node.js v22.23.2 的 Intl 数据生成 760 个正则对象（含地区短码正则）；1000 个香港节点名称触发 760000 次正则执行。关闭覆盖率后的独立计时中，构建中位数约 1.8 ms，5000 个混合名称匹配中位数约 145.8 ms（3 轮，不含完整 operator、网络与真实 common.js）。这些数据不代表 Surge/Sub-Store 设备耗时。
- 建议：优先减少每个名称的候选别名扫描；再按运行环境生命周期复用编译结果。构建成本远小于此样本的匹配成本，不能只加编译缓存就声称显著提速。
- 约束：必须保留最早位置优先、同位置最长别名优先、拉丁单词边界、短码位置限制和国旗回退，不能直接改成第一个命中即返回。
- 优先级：中；大量节点或低性能设备更值得做，少量节点无需过度设计。

#### 5. Homebrew：日常升级绑定完整诊断和深度清理

- 位置：`Homebrew/brew-upgrade-manager.sh:84`、`Homebrew/brew-upgrade-manager.sh:203`。
- 证据：每次完整运行均执行 `brew doctor` 和 `brew cleanup --prune=all`，没有分离快速升级与维护模式。
- 建议：保留当前完整流程，增加可选快速模式或独立诊断/清理选项；具体节省时间取决于本机安装量、缓存和磁盘，未实测，不承诺加速比例。
- 约束：默认是否继续完整诊断和清理需要用户确认。不要为提速同时并行执行两个修改 Homebrew 状态的升级流程。
- 优先级：低至中；属于可选工作量调整，不是纯粹等价的算法优化。
